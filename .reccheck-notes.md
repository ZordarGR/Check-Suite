## 1. What the tool is

An Electron 43.2.0 app that audits a night's POS receipts against protel's
`checkcharge1` report (`ΕΛΕΓΧΟΣ ΤΜΗΜΑΤΩΝ BY ROOM`, saved as `.oxps`). Two tools in one
page:

* **Department Check** — the receipt audit. Loads the `.oxps`, lists receipts per
  department, you search each paper serial and tick it. Corrections, manual entries and
  a printed sheet for reception come out the other end.
* **Tax Check** — a separate screen, cross-references a **rate list** (arrival/departure
  dates per room) against a **tax report**. Only run on nights where the main courante
  did not balance.

Alongside it: a nightly checklist with a desktop overlay, room nicknames, a watchlist,
per-user profiles, and `rc-tbind.exe` — a native helper that binds mouse buttons and key
combinations to protel shortcuts.

### The τ shortcut, the thing that has cost the most time

protel's invoice list jumps to the `ΤΕΛΟΣ ΑΝΘΕΚΤΙΚΟΤΗΤΑΣ` entry when you press the Greek
letter τ. It ignores an injected Unicode τ — it wants a real keystroke. So the helper
presses the **physical T key while Windows believes the keyboard is Greek**, then puts
the layout back. Everything hard about it follows from that.

## 3. How a release works

The workflow fires on a push touching `dist-win64/parts/**` or the workflow file. It
reassembles the parts, checks the sha, and republishes the tag.

`gh release create --latest` without `--target` tags the **default branch**, so a release
cut from a feature branch points at the wrong commit until it is merged. Merging fixes
it. This is why the workflow runs twice per release and that is fine.

### Building the installer (in the container)

**The script is in the repo now: `dist-win64/nsi/reccheck.nsi`.** Until 05/09 it lived only
in one container's scratchpad and was lost with it; a subagent reconstructed it from the
shipped 1.17.38 installer's decoded header (`nsisdump.py` beside it, written for the
purpose) and the rebuild was **byte-identical** to the shipped file — same sha256, same
Uninstall.exe — which is the strongest equivalence there is. `verify.sh` and `hdrdiff.sh`
re-run that proof against any two installers. Nothing about the recipe is from memory.

The stage is the previous installer's own payload: reassemble the parts, `7z x` into a
folder, delete `$PLUGINSDIR` (the script supplies the plugins) — Electron 43.2.0, ~306 MB.

```
scratchpad/stage/            the unpacked Electron payload, from the previous installer
dist-win64/nsi/reccheck.nsi  the NSIS script (NSIS 3.09-4, Unicode, solid LZMA)
```

The container needs: `apt-get install nsis p7zip-full mono-devel` (NSIS 3.09-4 is what
Ubuntu 24.04 ships, the same version the script was built for) and `npm i --no-save
playwright-core@1.49.1 @electron/asar@3.2.10` — **in ONE command**: a second `--no-save`
install prunes whatever the first one put there, which is how `playwright-core` vanished
mid-session and every browser harness went red with a module error.

1. bump `app/package.json`, `APP_VERSION` in `app/index.html`, `DisplayVersion` in the .nsi
2. `cp app/index.html "Departments Check.html"`
3. copy the nine files into `scratchpad/pack/`, `npx asar pack pack stage/resources/app.asar`
   (files.js, index.html, main.js, overlay.html, overlay-preload.js, package.json,
   preload.js, tray.ico, updater.js — 1.17.10 briefly made it eleven; 1.17.11 moved the
   Caps Lock icon into the helper and took it back to nine)
4. `cp app/rc-tbind.exe stage/resources/`
5. `cd dist-win64/nsi && makensis -DSTAGE=<stage> -DVERSION=<x.y.z> -DICON=<repo>/app/reccheck.ico
   -DOUTFILE=<out>/RecCheck-Setup.exe reccheck.nsi` — ~5 minutes. **Wait on the process,
   not on the call.** (And not `time makensis` from a `sh` script: dash has no `time`.) Backgrounding it a second time (`nohup … &` inside an already
   backgrounded call) reports exit 0 the instant the shell forks, and the half-written
   `RecCheck-Setup.exe` sitting there looks like a finished 7 MB build. Poll `pgrep -x
   makensis`. A real one is ~93 MB; the log's last line is `Total size:`.
6. **unpack the result and verify it** before splitting — `7z x` the installer, then
   `npx asar extract` the `resources/app.asar` inside it and check `APP_VERSION`, the file
   count, and that the page is byte-identical to `app/index.html`. `strings` proves
   nothing: the payload is solid LZMA, so nothing inside it is greppable, and neither is
   the `DisplayVersion` the .nsi writes.
7. `split -b 20971520 -d -a 3` into `dist-win64/parts/`
8. update `VERSION` + `SETUP_SHA256` in the workflow and `update/latest.json`

### Two kinds of update

* `type: "full"` — 90 MB installer. Needed whenever `main.js`, `preload.js`, the helper or
  anything outside the page changes.
* `type: "html"` — ~370 KB. Only `Departments Check.html`. `engine` names the minimum
  engine version; an older engine takes the full path instead and can never strand itself.

An html update is promoted only if its version beats the installed `pkgVersion`, so
`APP_VERSION` in the page and `version` in the manifest have to move together.

## 4. Landmines — every one of these cost real time

* **Clicking a button in RecCheck makes RecCheck the foreground window.** Obvious once
  said, and it made the whole live-feed button dead on arrival in 1.17.27: `ReadInhouse`
  opened with `GetForegroundWindow()`, so the press it was reacting to had already put
  RecCheck in front and the read came back "that is not protel". DEBUG's `readlist` gets
  away with the foreground only because it counts down first and he switches over — a
  button has no such moment. **He ran it, got exactly `protel said: that is not protel`,
  and then asked the question that located it** — "does it take the list from whatever
  window is in front?" The failure was on his screen; the code answered why. (An earlier
  note here said he found it by asking rather than by running. He ran it. Corrected.)
  Anything triggered from RecCheck's own UI must find its target window by hunting for
  it, never by asking what is in front.
* **A stub can hide the only thing that matters.** `test/browser/live.js` proved the
  parsing, the refusals and the ledger writes — and stubbed the bridge, which is exactly
  where the bug was. Everything downstream of `window.reccheckShortcuts.inhouse()` was
  correct; the call could never return anything. **This class of fault — whether the
  helper is looking at the right window at the moment it is asked — is not testable in
  this container at all**, and no harness here should be described as covering it.
* **In an MDI app, the biggest list under the frame is not the list in front.** protel's
  reports are MDI children. A restored window sits on top of a maximised one, so picking
  the largest `SysListView32` under the frame reads the window BEHIND. And the frame's
  caption names a child only while that child is maximised — restore it and the caption
  names nothing, so the read cannot even report which list it got. Scope to the active MDI
  child (`MDICLIENT` → `GetWindow(…, GW_CHILD)`) and report THAT window's caption. Found
  by him on the second live run, before a line of it was wired to the ledger.
* **A tripwire that matches one syntax checks only that syntax.** `test/scopecheck.js`
  compared the two language tables with a regex for QUOTED, DOTTED keys (`"menu.audit":`)
  — the shape `T` uses. `I18N`'s keys are bare identifiers (`live_read:`), so all 112 of
  them, both languages, were invisible to the guard that exists precisely because keys had
  drifted into one language before. It now walks the literal instead of matching lines,
  skipping strings whole so a value like `"protel said: "` cannot be mistaken for a key.
  Found while adding two keys by hand to two tables — which is exactly the moment it was
  supposed to be watching.
* **ASAR integrity.** The shipped exe carries an `/INTEGRITY/ELECTRONASAR/` resource, but
  the fuse `embedded_asar_integrity_validation` is **DISABLED** (sentinel
  `dL7pKGdnNz796PbbjQWNKmHXBZaB9tsX`). Repacking `app.asar` is therefore safe. Verify
  before assuming.
* **Mono's BCL is bigger than .NET Framework's.** `mcs` compiles against Mono; the helper
  runs on .NET Framework 4.8. `body.Split(',')` bound to `String.Split(char,
  StringSplitOptions)`, which 4.8 does not have — the JIT resolves every token in a method
  before running it, so the whole of `ParseBind` threw `MissingMethodException` on first
  call and the helper died 53 ms in with exit `0xE0434352`. Hidden for three versions
  because a second bug meant nothing was ever bound, so the helper never started. **This
  is what `build-check.py` exists to prevent.**
* **A test that lifts a function by text proves that function, not its caller.** The
  movements panel showed nothing for two versions. A harness lifted `roomMoves` out of
  the page, drove it with a real ledger, produced correct pills, and I reported the panel
  was not broken. It was: `renderMoves` called `liveReceipts()`, which does not exist
  anywhere — the real name is `checkableList()` — so it threw a `ReferenceError` after
  appending its title and before the first pill, and `stage()` swallowed it. His own
  DEBUG report said `43 pills` while the panel was blank; that contradiction was the
  evidence and I did not read it. **Lift the function that is actually called, or check
  the scope.** The scope check below finds this in a second.
* **The tax half is namespaced; the audit half is not.** Everything under `#taxScreen`
  is prefixed, but the audit's own chrome is written on bare element selectors — `header`,
  `header h1`, `.btn`, `.acc`. The tax page has a `<header>` and an `<h1>` of its own, so
  it had been rendering them as the audit's sticky, blurred, bordered, amber-monospace,
  `white-space:nowrap` app bar since the two halves were merged. `#taxScreen header h1`
  only overrode the properties it happened to re-declare; the rest leaked. Between 901 and
  ~1090 px — where the help panel takes 300 px and leaves under 600 — that pushed the whole
  page past the window. **A rule under `#taxScreen` must state every property the bare
  selector sets, not just the ones being changed.** `.acc` still inherits the audit
  accordion's panel background and border; verified harmless on screen, so left alone.
* **One row could wipe the whole ledger, and nothing would say so.** The pruning loop in
  `saveMoves` took its floor from **the newest departure in the ledger** minus a year.
  That hands the decision to whatever the furthest-future row says. protel prints an
  open-ended reservation as `31/12/99`, and `dkey` (5288) reads a two-digit year as 20xx
  with no upper bound — so `31/12/99` is **20991231**. One such row set the floor to
  20981231 and deleted every real 2026 stay; the poison row survived the cull because its
  own date is above the floor, so **every later rate list wiped the ledger again**. The
  panel would have gone empty for ever with nothing on screen to explain it.
  Reproduced against the shipped code before changing it, and shown fixed after. The floor
  is anchored to the LIST'S OWN business date now — a real date no single row can drag —
  and with no date nothing is pruned at all. A stay with **no** departure date is also no
  longer dropped: `d||0` put every one of them below any positive floor, and a stay protel
  printed without a departure is not an old stay. **It was not firing on his ledger**
  (span 20260814..20260925, floor 20250925) — a landmine, not a live fault.
* **The 03:30 boundary is visible between 03:30 and 07:00, and only there.** At 06:46 on
  03/09 the tool's current night is 03/09, so a loaded 02/09 report is labelled amber
  "last night" where the old 07:00 boundary made it green "tonight". The file browser's
  TONIGHT badge (`bnKeyOf(f.mtimeMs) === bnKey()`) moves with it. Neither touches which
  pills are drawn — the set comes from `MODEL.reportDate` — but it is what he will see
  first if he reads the header as disagreement.
* **Do not derive a wall-clock boundary by subtracting absolute time.** Both day keys were
  `new Date(now - h hours)` read in local fields. Correct on 363 nights and a whole hour
  wrong on the other two: measured against Greece's real transitions, the shift reset went
  at **06:00** on 25/10/2026 and **08:00** on 28/03/2027, and the working night at 04:30
  instead of 04:00 in spring. Compare the local hour to the boundary and step the local
  DATE back instead — that cannot drift, because 07:00 is 07:00 on the wall whatever the
  offset did. On the spring night 03:30 does not exist, so the working night turns at
  04:00, the first local minute that does; that is right, not a compromise. `test/dst.js`
  fails on the old arithmetic and passes on the new.
* **He was right about the shape and it is worth keeping.** The reset is a stored day key
  compared on a 30 s poll, NOT a "fire at 07:00" condition — so a machine asleep or an app
  closed at 07:00 still clears at the next look, and a clock corrected by its time server
  is simply re-read. That half was never the fragile one. The bug lived entirely in how
  the key was derived.
* **The helper's pipe was never carrying anything but ASCII, so nobody noticed it was
  wrong.** `Say()` wrote through `Console.Out`, which encodes with the CONSOLE's code page
  — not UTF-8 on a Greek Windows — while `main.js` decoded the pipe as UTF-8. Every verb
  until now answered in ASCII (`RCTBIND OK v15`, hex handles, class names), so it never
  showed. The list read is the first thing to send a guest name back, and he said it
  himself: the list has Greek in it. It writes UTF-8 bytes straight to the handle now.
  **And the Node side decoded each chunk separately** (`out += d`), which destroys any
  character whose bytes land either side of a chunk boundary — all seven handlers collect
  the buffers and decode once. `test/stdout.js` splits a Greek name mid-character on
  purpose and checks it survives.
* **A blind search-and-replace across seven handlers broke four of them, and `node --check`
  passed.** They pushed into `chunks` while their closures still read `out`, a binding that
  no longer existed — a `ReferenceError` at the moment the user pressed the button, in code
  that parses cleanly. Same shape as `liveReceipts`. The harness drives the real handlers
  with electron and `child_process` stubbed, which is what caught it.
* **A P/Invoke whose return value is thrown away decides things by accident.** `readlist`
  opened protel with VM_OPERATION|VM_READ|VM_WRITE and no query right, then called
  `IsWow64Process(proc, out wow)` and **discarded the BOOL**. That call REQUIRES
  PROCESS_QUERY_INFORMATION or PROCESS_QUERY_LIMITED_INFORMATION, so it fails, never
  writes the out parameter, and `wow` stays false. `target64 = (IntPtr.Size == 8) && !wow`
  then answers TRUE on 64-bit Windows — while protel is `PROT32`. A 64-bit LVITEM handed
  to a 32-bit list control puts `pszText` in the alignment padding: **NULL**. On an
  owner-drawn list that null reaches protel's own `LVN_GETDISPINFO` handler. Found by the
  pre-push audit, confirmed by two more agents that tried to refute it, and never shipped.
  Now: the query right is asked for, both `IsWow64Process` calls are checked, the OS's
  bitness is established separately from ours, and **the read is refused rather than
  guessed** if either call fails.
* **A test of the parts is not a test of the choice.** `test/lvitem.cs` proved both LVITEM
  layouts were built correctly — seventeen assertions, all passing — and was blind to the
  wrong one being selected. `TargetIs64` is now a pure function precisely so the DECISION
  can be pinned, across all four combinations of OS and target bitness.
* **A guard with hardcoded line numbers stops guarding silently.** `test/scopecheck.js`
  sliced the page at `lines.slice(1322, 4937)` to find the renderer's IIFE. The page grew,
  the window drifted off the declarations, and it began calling declared things undefined.
  It searches for the block now. It also strips comments first — prose contains things
  that look like calls, and it was reporting `all` as undefined because a comment said
  "at all (65, 94, ...". A checker that cries wolf over its own commentary gets ignored.
* **A truncated diagnostic produces a truncated diagnosis.** `movesReport` printed
  "stays near this night" and cut it at 40 rows. On 02/09 that cut at room 153, and the
  conclusion drawn from it — that every pill above 153 must come from the name-change
  deduction — was right about the rooms it could see and wrong to be stated as the whole
  cause. Removing the deduction did not stop the phantom departures, because the OTHER
  source was never visible in the report: **stays whose recorded departure date is simply
  out of date.** Nothing is deduced now; a ledger entry written by an old rate list just
  keeps saying what that list said. 1.17.21 prints every pill with the date of the list
  that wrote it and counts how many are older than the newest, which is the difference
  between the two causes on one line. **Never diagnose from a report that elides.**
* **A name change is not a date. Third time.** 30/08: a rule that ended a stay when a
  room charged under an unrecognised name made 83 phantom departures. It was removed from
  the ledger writer — and the same inference survived in `roomMoves`, adding a dashed
  TURNOVER pill for any room whose department-report name differed from the cached one.
  On 02/09 the last rate list loaded was 31/08, so every real changeover of 01/09 and
  02/09 read as a name change: rooms **65, 94, 124, 129** — with no arrival or departure
  on that night in the ledger at all — were all claimed to have left and been re-let.
  Proved from his own DEBUG dump: those rooms are pills, and they are absent from the
  same dump's list of stays within three days of the night. **Dashed does not help — a
  turnover pill claims a departure.** Gone in 1.17.17. `ROOMS[].movedOn` is still stamped
  and now read by nothing.
* **A room number is not a stay.** The receipts dot on a departure pill was built from
  `effRoom(r)` alone, so any live receipt for that room number lit it. The moment a room
  turns over — and with no rate list since the arrival, a turned-over room still shows as
  a plain departure — the dot lands on the NEW occupant's receipts, which is paper he
  must not throw away. It matches on the departing guest's name now, through
  `leavingIndex()`/`isLeaving()`, the same index behind the red mark in the search
  results, which was specified against exactly this mistake.
* **`display:none` in a stylesheet is not cleared by `style.display = ""`.** That only
  removes the inline override. `#notThereBtn` was never once visible. Toggle a class.
  And **assert on `getComputedStyle`, never on `el.style.display`** — the latter reads
  `""` precisely when the rule is hiding the element.
* **raw.githubusercontent caches the manifest ~5 minutes per regional edge.**
  `cache: "no-store"` does not bypass it; a unique query string does. This hid two
  releases.
* **An `HKL` is `(device << 16) | language id`.** Comparing whole handles reports a
  working layout hop as failed. Compare the low word.
* **`GetKeyboardLayout(0)`** reports the *calling* thread's layout. A thread id of 0 made
  a hop that never happened look successful.
* **`SendInput` is not synchronous.** Checking the queue immediately after it returns
  reads empty because the key has not arrived yet, not because it was consumed.
* **`dir` on a folder you cannot list prints *File Not Found*, not *Access is denied*.**
  His `dir C:\Windows\System32\spool\PRINTERS` on 05/09 printed a *Directory of* header
  and *File Not Found*; it was read here as "listable and empty". 1.17.45's capture then
  got `EPERM` from `readdir` on the same folder. Only a program's own attempt answers a
  permission question; a shell's wording does not.
* **A rule that names its elements one by one goes stale the moment one is added.** Three
  rules sized the home buttons as `#auditBtn,#alertsBtn,#statusBtn`. ALERTS was born
  outside all three (1.17.33), REPORTS again (1.17.50) — spanning the whole window. Name
  the PLACE (`#menuScreen > .mItem`), not the members. Same shape as the language-table
  tripwire that matched one key syntax and the guard with hardcoded line numbers.
* **AND A THIRD AND FOURTH TIME, both in one night (1.17.53).** `norm()` was a two-way
  switch that read any unknown profile as the Department Check's (7m). And `beforeprint`
  exempted the Tax Check by a body class, so REPORTS — added in 1.17.50 — printed the
  CORRECTIONS over its own departures sheet (7n). **An exception list never covers what is
  added after it.** Name the intent, or name the place; never the members.
* **Do not name a harness after a screen.** `test/reports.js` guarded `feedStays` with 51
  assertions until 1.17.50 gave the redacted departures print the same filename and wrote
  over it. `run.sh` then ran the survivor twice and the README kept a row for each, so the
  repo claimed a guard it did not have and nothing said so. Name a harness after the thing
  it holds the line on (`feedstays.js`), and if `run.sh` lists a name twice, that is the
  symptom.
* **Out of bounds is not only off-screen.** A layout sweep that asks "does the page scroll
  sideways / is anything past the right edge" passes an element that is merely far wider
  than the column it belongs to, as long as it stays inside the window. Ask what it should
  line up WITH.
* **The two page copies drift.** `Departments Check.html` was left at a pre-1.16.1 state

* **The script blocks are IIFEs** — nothing is on `window`. To test, inject a probe before
  the final `})();` on a copy.
* **jsdom needs an http origin** for `localStorage`; on `file://` it throws.

## 5. The build guard

`app/build-helper.sh` compiles and then runs `app/build-check.py`, which reads the
compiled assembly's `#Strings` heap and fails on any name not in `app/bcl-allow.txt`.

Adding a name to that file **is** the moment to confirm the member exists in .NET
Framework 4.8, because nothing else in the build will tell you. It is a name-level check,
not a signature-level one — a tripwire, not a proof. It also flags our own new method
names, which is the accepted cost.

Reintroducing the `Split` bug makes it exit 1 naming `StringSplitOptions`.

## 7a. The night of 05/09 — three symptoms, six faults

He reported three things in one line: *"you removed the button, there is no watch log in
the debug menu and when opening tax check there is nothing shown when i open the inhouse
list"*, and then, from the tax screen: *"Departure report 05/09/26: 41 rows, 0 stays
recorded. 2 holding-room row(s) ignored."*

That last line is the only hard datum in the whole night, and it settles more than it
looks. `applyReport` builds it AFTER the write, from a capture file — `readReportLive` and
`readMovesLive` exist but are called from nowhere, so the only path into `applyReport` is
`ingestCaptured`, fed by the helper's `rc-list-DP.tsv`. **The watcher had worked.** The
forty-one rows are real, they parsed, and they were handed to `feedStays`.

What was actually wrong, all of it verified by reading:

**1. The panel is drawn from the ledger and nothing ever told it the ledger had changed.**
`renderMoves()` ran in two places: inside `refresh()`, and after the ledger-reset button.
Every writer of the ledger now lives in the *other* IIFE and could not reach it. So the
pills were frozen at whatever the ledger said when he last loaded a department report, and
a departure report opened in protel afterwards changed nothing on screen. This is *"i've
opened departure report of 4/9 … but departures do not show"*. Fixed with `__rcMovesChanged`
— the narrow door. `__rcLiveNames` refuses to redraw because `renderAll()` calls
`showScreen("app")` and would throw him off the screen he is working on; `renderMoves()`
does no such thing.

**2. The watcher goes permanently deaf and cannot recover.** `WinEventCallback` tested
`watchSeen >= WATCH_MAX` at the very top, and the counter's only reset lived inside
`AppendWatch` — which that same return made unreachable. The four-thousandth captioned
event of the run therefore did not end a shift's logging, it ended the watcher: no more log
lines and no more `evWantTag`, which is the field the entire automatic feed hangs on. The
07:00 reset could never fire again. The helper starts at login and is not restarted, so
this was a one-way switch. Worse, `watchSeen++` ran BEFORE the caption de-dupe, so protel's
frequent title restatements — which the code's own comment says it makes often — each spent
a unit of the budget and produced no line, so the log's length never showed how fast it was
going. **This is the best candidate for both the empty watch log and the in-house list
showing nothing**, and it fits the shape exactly: an old capture file still on disk from
when the watcher was alive, nothing new arriving. Not confirmed on his machine — nothing
here can be — but the latch itself is not in doubt.

**3. Four captures, one line, fixed order.** All four files are collected on the same tick
and each ingest writes the same `#liveSay`. `LIVE_TAGS` ends with `DP`, so a departure
report always had the last word — and the files live twenty hours, so the first tick after
the app starts replays yesterday's report over the list he opened a second ago. Now sorted
by capture time, so the newest has the last word.

**4. "0 stays recorded" was the same sentence for opposite facts.** `feedStays` returned the
count of entries it CHANGED. A report the census already agreed with changes nothing, so a
complete success and a dead write printed identically. Now counted apart: made, corrected,
already known — and a write that threw says so instead of returning an innocent nought.
On a tie the census wins by design, so on a normal night the honest answer to a departure
report really is "41 already known".

**5. "2 holding-room row(s) ignored" was not about holding rooms.** One counter served
three unrelated drops — a room cell that is not a room, an arrival date that would not
parse, and a row that came back half-read. Room 9000 being skipped is routine; forty rows
failing to parse is not, and the same sentence covered both. Split, with `cancelled` shown
too — it was computed and never printed. And `{0} rows` was fed `recs.length`, the records
BUILT, so the arithmetic on the line could never be made to add up. Both numbers now.

for all of them — a claim about protel made from no evidence, when three of the four mean
something is wrong with the tool. Each says which now, and the helper writes a `HOOKS` line
whenever the set of processes it is watching changes, including naming the needle when it
is watching nothing. `#scWatch`, `#scLog` and `#scRead` also returned in silence when the
door was missing: a dead press is the one answer a diagnostic may not give.

Also removed: `focusSpec` was declared twice, byte for byte, in `main.js`. Behaviour was
correct — JavaScript keeps the second — but it is the line that decides whether the
watcher runs at all, and an edit to the losing copy would have gone nowhere silently.

A new session took over from `.reccheck-notes.md` and the branch

then given the rule-6 check it had not had: eight adversarial lenses over 1.17.38 and the
never-checked 1.17.37, and three sceptics per finding. The fan-out ran into his session
limit twice on a four-CPU container, so the sceptic stage was finished by reading and by
running the shipped code here, not by more agents. All verified unless marked.

**In 1.17.38, its own claims:**

1. **`helper=vNN` could never print.** `sc-helper`'s snapshot never copied `TAUINFO.ver` —
   the release's headline field was dropped one hop before the page, and the comment in
   `helperDetail` asserted a data path that did not exist. Same shape as the `specs=` bug
   the same release fixed. Reproduced by `test/helperline.js` before the fix.
2. **The status and ping verbs report the exe on disk, not the resident.** Both run a fresh
   copy of `rc-tbind.exe`; neither asks the process in memory anything. Even forwarded,
   `helper=` would have claimed a fact about the resident. Labelled `exe=` now.
3. **"started" read as "Running — your bindings are live."** That state is written the
   instant the helper is SPAWNED and never revisited (detached, no exit listener), and the
   press's probe ran `ping`, which proves the exe runs and nothing else. A helper that died
   53 ms in would have shown green all night with its crash text under it. The press asks
   `status` now — the verb that LOOKS FOR the resident's window, the one fact about the
   process in memory that can be established from outside it — and the verdict is built on
   that answer: found → running; not found → crashed if there is a crash file, "started
   and stopped" if RecCheck spawned it, with a 2.5 s grace after a spawn during which the
   window's absence is not yet a verdict ("checking…", asked once more).
4. **A spawn Windows refuses is an event, not a throw.** `spawn()` reports EACCES through

   main process and the state stayed "started". Listener added; state "spawn-failed".
5. **`binds=` was printed from the specs assigned BEFORE the write**, so a binds file that
   could not be written had its intended contents shown as published, and "COULD NOT
   WRITE" never left main.js. Assigned only after the write; forwarded; printed.

   helper would not re-read that caption, so the claim stood all night. Each ingest
   answers "ok" or why not now, the answer rides on the entry ("not taken: the read was
   cut short"), the row count shows "180 of 250", and the lead word is "from protel:".
7. **"nothing captured from protel yet — open a list" was printed for the tool's own
   failures**: a capture file it could not read, a file older than twenty hours, no
   app-data folder. `sc-listfile` says which now; a file that cannot be read keeps what
   was held and says so; the promise of a re-capture is gone (the helper does not re-read
   a caption it already took, see the queue).

   the tag test, so once a report's caption was in `lastTitle` every restatement of it was
   dropped before the capture saw it. v23 had the same order, but the Static/Button churn

* **"The spooler will not give up the content. Full stop." was TOO STRONG — my error, say

  write paths for a job you are SUBMITTING, not read paths for one you are watching. **But
  a job object exists**: `OpenPrinter` and `OpenPrinter2` accept the name form
  `"PrinterName, Job xxxx"`, and `ReadPrinter` documents that same form. Two things gate
  it, and neither is a flat no: the flag that makes `ReadPrinter` read the spool file
  (`DI_READ_SPOOL_JOB`, `winsplp.h`) is **not documented on Microsoft Learn at all**, and
  access is gated by `JOB_ACCESS_READ`, which per MS-RPRN is held by **the job's creator**
  and Administrators. **protel prints under HIS Windows account, so he IS the creator** —
  the "another process's data" framing does not describe his case. Status: undocumented
  and unestablished, NOT impossible. Do not repeat the flat no.
* **The listener: confirmed, but *inferred*, not verified.** The Win32 page for
  `FindFirstPrinterChangeNotification` states **no required access right whatsoever**; that
  `PRINTER_ACCESS_USE` suffices rests on MS-RPRN plus `OpenPrinter`'s documented default
  (`pDefault` NULL → `PRINTER_ACCESS_USE`). Pure event handle — `WaitForSingleObject`, no
  message loop, no window. The job id comes back as `PRINTER_NOTIFY_INFO_DATA.Id`.
  **Two corrections to what was said above:** there is **no `JOB_NOTIFY_FIELD_SIZE`** (byte
  count is `JOB_NOTIFY_FIELD_TOTAL_BYTES`, 0x16), and these are **`winspool.drv`, not
  `user32`** — the helper's existing user32 P/Invoke experience says nothing about whether
  this works. Also: `FindNext` "typically provides data only for the fields that changed",
  so the document name may NOT arrive on the `ADD_JOB` event; resolve by
  `PRINTER_NOTIFY_OPTIONS_REFRESH` or `GetJob` on the id. `TOTAL_PAGES` may be 0 at submit.
  `PRINTER_NOTIFY_INFO_DISCARDED` must be handled or a resident helper goes permanently
  deaf after an overflow — **the same latch shape as 7a fault 2**; `FreePrinterNotifyInfo`
  or it leaks.
* **The spool folder: the traverse-vs-list reading HELD.** KB 2762101 enumerates the
  default Users ACE on the spool directory as Read attributes, Read extended attributes,
  Create files/write data, Create folders/append data — **no "List folder / read data"**,
  which is exactly his `EPERM`. It lists no traverse either, but that is moot: Users hold
  **BypassTraverseChecking** by default, which "causes the system to skip all traversal
  access checks" while not allowing a listing. **So the folder is not the gate. The file's
  own DACL is, and Microsoft documents NOTHING about the `.SPL`/`.SHD` owner, DACL or
  CREATOR OWNER inheritance — nor the five-digit filename.** Genuinely unknown, and
  undocumented internals are a reason not to build on them even if a test passes.
  *Weakest link: KB 2762101 is a Windows SERVER KB; its applicability to his Windows client
  is inferred.*
* **A route-killer nobody had raised:** if the target printer is a **shared queue hosted on
  another machine**, the documented File and Print Sharing firewall exception must be
  enabled ON THAT MACHINE or the notifications silently never arrive — and that needs an
  admin. **Establish local port vs network share before anything else**, it is one look at
  the printer's properties and it can end the route on its own.
* **The test that would settle the ACL, if he ever revives this** — sharper than the one
  offered him: hold one job in the queue, take its `JobId` from `EnumJobs` (no admin, no
  folder access), then `CreateFileW` on `…\PRINTERS\<JobId padded to 5>.SHD` with
  `GENERIC_READ` and full share flags, and record the RAW Win32 error. Four codes
  discriminate four hypotheses: `SUCCESS` = open-by-name holds; `5` = the file DACL rules
  it out regardless of the folder; `32` (sharing violation) = the ACL allowed it and only
  the spooler's handle blocks it; `2` = the filename assumption is wrong on his machine.
  **`.SHD` not `.SPL`** — small, written once, less likely to be held open. **The raw Win32
  error, not Node's `errno`** — Node collapses 5 and 32 into shapes that mislead. Still a
  build, still needs his go.

  with document names, for jobs submitted by OTHER Windows accounts. Moot while protel runs

### An installation overlay — BUILT, 1.17.29

His words, 04/09: *"when installing, it would be nice to have an overlay (during the
installation process) that shows the installation progress instead of nothingness, im
thinking it would be cool to have the icon in the middle and the progress bar being a

had to ask where it was.

**It is a separate process, and the plan recorded here before was wrong.** These notes had
`rc-tbind.exe` drawing it, on the reasoning that the helper outlives RecCheck. Reading the
.nsi properly kills that: the installer's FIRST act is

```
nsExec::Exec 'taskkill /F /IM RecCheck.exe'
nsExec::Exec 'taskkill /F /IM rc-tbind.exe'
```

because Windows will not overwrite a running exe. So the helper is not merely at risk, it
is deliberately killed. RecCheck instead copies it to `%TEMP%\rc-splash.exe` and runs
`splash` from there just before exiting: `taskkill /IM` matches the IMAGE NAME, so the
copy is not what it is looking for, and nothing in TEMP is touched by the install.

**The ring travels; it does not fill, and that is deliberate.** `spawn(setup, ["/S"])` is
a silent NSIS run. It reports progress to nobody, and RecCheck is gone 300 ms later
regardless. A ring filling 0→100 here would be a number invented to look like a
measurement — the one thing his rules forbid outright, and the same instinct that put 83
departures on his panel. So the arc travels: it says work is happening, which is exactly
the "instead of nothingness" he asked for, and claims nothing it does not know. **The
download half already has a real percentage** and already shows it in the app
(`updater.js:112-126` → `#updBox`) before any of this starts.

**Palette, from the update button itself** (`app/index.html:610-615`): disc `#101d33`,
the track the arc runs on `#2f5f9e`, the arc `#286edc` — the button's own glow. COLORREF
is `0x00BBGGRR`, so the constants read reversed.

**It cannot break anything, by construction.** Click-through, never activated, so it
cannot take a keystroke or a click from anything — protel included. If the copy fails, the
spawn fails or the drawing throws, the install proceeds exactly as before: nothing waits
on it and nothing checks it. It closes when RecCheck comes back — the installer relaunches
it as its last act — and on a 240 s timeout regardless, so a failed install cannot strand
it on screen.

**Three bugs in it, found by the check he asked for before merging — all in code an hour
old, none of it shipped.** Worth listing, because each would only have shown itself on his
machine, mid-install, with nobody able to see the code:

1. **A GDI object leaked every frame.** The disc brush was still SELECTED into the DC when
   the `finally` deleted it, and GDI silently refuses to delete a selected object. At 25
   frames a second for the length of an install that walks toward the 10,000-handle
   process quota, after which `CreateSolidBrush` returns null and the overlay quietly
   falls apart. Fixed by deselecting into stock objects before the finally.
2. **The whole process table was walked 25 times a second**, to ask whether RecCheck was
   back — on his machine, while it extracts 300 MB. Now once a second, which is still far
   more often than RecCheck can come and go.
3. **The hand-off countdown could only ever end on an exact zero.** `splashBackMs == 0`
   after subtracting the frame time works only because 40 happens to divide 1200. Change
   either number to a pair that does not divide and the overlay hangs until the 240 s
   timeout. It is a flag and a `<= 0` now, not an arithmetic coincidence.

And a fourth, in the test written to catch them: the "never comes back" case passed
RecCheck as never leaving, so it re-ran case two and passed for the wrong reason.

### The room database on disk — BUILT, 1.17.31

His call, 04/09: *"we need the rooms that have been fed by protel to persist somewhere in

**It is obfuscation, and it is never called anything else.** `rooms.dat` in

password is never wanted, **DPAPI** ties the file to his Windows account with nothing to
type at all.

### The tool is told, it no longer asks — 1.17.35

His, 04/09, after asking how often a ping would have to run to catch a list opened for two
seconds: *"when a user opens protel the tool knows and scans the list opened"*.

**THE PAGE NO LONGER DRIVES PROTEL AT ALL.** The helper is already resident — it is what
serves the tau shortcut — and it already holds a WinEvent hook on protel's SHOW, HIDE and
NAMECHANGE. It is therefore TOLD, in milliseconds, when a list appears. It reads it there
and then and writes the rows to `%LOCALAPPDATA%\RecCheck\rc-list-<tag>.tsv`; RecCheck
collects that file through IPC, which launches nothing and touches protel not at all.

**That is what makes a two-second window work.** The rows are taken at the moment it opens,
so they are still there to be collected long after it has closed. Polling could only ever
catch such a window by luck — at five seconds it would miss most of them.

**It also settles the departures cadence he raised.** *"departures wont change unless
something urgent has happened"* — a departure report is now read when he opens one, which is
exactly when it changes, and never in between. No timer, no schedule, and no need for the
manual first read he was ready to settle for.

**Where the cost actually is, measured off his own runs** (~0.57 ms a message):

| | protel |
|---|---|
| finding the window | **nothing at all** — class names, captions and Z-order are window-manager reads |
| a ping (rows + columns) | 3 messages |
| a full in-house read | ~1500 messages, plus a scratch page allocated and freed |

So the ping he proposed is real and is built (`peek`, one process for all four lists), but
the event hook makes it mostly unnecessary: nothing needs to ask whether a list is open when
protel says so.

**THE READ DOES NOT HAPPEN IN THE CALLBACK.** A WinEvent callback runs on the hook thread; a
full read is fifteen hundred blocking messages into protel. Doing that inside the callback
would stall the delivery of every later event and put a long synchronous conversation with
protel in the worst possible place. The callback does one field write; `WatchLoop` does the
reading, on the same thread but between pumps. Two guards on top, both about protel: the
same list is not re-read within four seconds however often protel shows it, and a caption
unchanged since the last successful read is not read again at all.

### The arrival and departure reports feed the ledger — 1.17.34

Unblocked by his two answers, 04/09: **the move direction was read right the first time**
(column 0 is the room being left, 2 the room taken), and **"9000 is a holding room, ignore
it"**.

**They do NOT go through `saveMoves`, and that is the entire design.** `saveMoves` and
`detectMoves` are written for the IN-HOUSE list, which names every occupied room, and both
reason from ABSENCE — a room the list does not mention is a room the guest has left. An
arrival report names thirty rooms out of two hundred. Putting one down that path would read
as a hundred and seventy people leaving at once and mark half the hotel as having moved: the
30/08 failure, reproduced deliberately. So `feedStays` is a separate writer that states only
what its rows state, adds and corrects, and never deletes, prunes or infers.

**Each report carries only ONE of the two dates**, the other being its own, from the caption.
Arrivals: name 1, room 3, occupancy 5, **departure** 6, status 10 — the arrival IS the report
date. Departures: name 0, room 2, occupancy 4, **arrival** 5, status 10 — the departure IS the
report date. Corroborated twice over: his 23:17 reads, and protel's own home screen, where the
Arrivals panel's date column reads *Dep.* and the Departures panel's reads *Arr.*

**`seen` is the night the READ happened, not the date on the window.** That distinction is a
bug the audit caught: stamping it with the caption's date meant a report he had opened for a
FUTURE day wrote entries stamped in the future, which the seen-guard then refused to let any
later read correct. The stay would have frozen at whatever that window said.

**Four lists on every tick would be four helper launches every five seconds** — some thirty
thousand across a shift. The in-house list keeps the cadence he asked for; the moves window
and the two reports take one tick each in rotation, so each is read about every fifteen
seconds. A failed hunt still costs protel nothing, so the rotation is about his machine.

### What the second pre-merge check found — and the one that mattered

Same shape: four adversarial lenses, three sceptics per finding. Six real, and one of them was
mine at its worst:

**The report names were being pushed through `__rcLiveNames` — the CENSUS door.** That door
says "this is who is in this room now", and `syncRooms` then reads a stored name that does not
match the receipt as a room that has turned over: stamping `movedOn` and **deleting the
nickname**. A departure report names the guest who has LEFT. On a changeover the two reports
name different people for the same room and would have fought over it every fifteen seconds.
It is removed outright — the in-house list is the census and already supplies the names; the
reports are not, and have no business writing them.

The other five: `seen` stamped from the caption (above); `RPT_SIG` set BEFORE the write, so a
failed `feedStays` meant that report was never retried; an empty status read as "not
cancelled" and an empty name as a guest, when `ReadCell` returns "" for every failure it has;
one throw in the in-house read stopping the moves and both reports for the life of the app,
because they were awaited bare; and the ledger reset not clearing what the loop remembers, so
he could empty the ledger and watch it stay empty while protel sat there full.

**And one finding was refuted by the code being right and my TEST being wrong**: an arrival row
with no departure date. That is not a failed read, it is how protel prints an open-ended stay,
and the ledger already treats an absent departure as one protel has not stated. Recorded, and
it must not wipe a departure something else already knew.

**THE ONE THAT SURVIVED THE VERIFICATION, and it is the sharpest thing either audit found.**
`seen` is a business night on BOTH sides — `saveMoves` stamps it with the in-house list's
date, `feedStays` with tonight — so through a whole shift the two are the same number and the
recency guard `night < cur.seen` is a TIE that never fires. The line after it then took the
report's departure unconditionally.

That matters because the two sources are not equally fresh. **protel's in-house list is a
census this reads again every five seconds; a report window is a snapshot from whenever he
printed it.** A departure report printed at six in the evening could therefore overwrite an
extension the census had already picked up at one in the morning — and `roomMoves` puts a pill
on any departure whose date equals tonight. **A phantom departure on his panel, which is the
failure that has cost him twice**, reached by two writers agreeing about the date and
disagreeing about the fact.

Within one night a report may now CREATE a stay and may FILL a blank, but it may not overwrite
what the census holds; on a strictly later night it is the newer word and wins. The comment
above `feedStays` had claimed exactly that contract from the start — the code simply did not
implement the tie.
