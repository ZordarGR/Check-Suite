# RecCheck — working notes

A hidden dotfile, deliberately. It is not in the nine files `app.asar` packs, so it never
reaches an installed copy; it exists so a fresh session can pick this up without
re-deriving any of it.

Owner: Dimitris (`ZordarGR`), night auditor, Kernos Hotel, Malia. Repo `ZordarGR/Check-Suite`.
The work machine is not his, so nothing may be installed or changed on it — every build,
release and test happens in the cloud container.

Last release: **1.17.9**.

---

## 1. What the tool is

An Electron 43.2.0 app that audits a night's POS receipts against protel's
`checkcharge1` report (`ΕΛΕΓΧΟΣ ΤΜΗΜΑΤΩΝ BY ROOM`, saved as `.oxps`). Two tools in one
page:

* **Department Check** — the receipt audit. Loads the `.oxps`, lists receipts per
  department, you search each paper serial and tick it. Corrections, manual entries and
  a printed sheet for reception come out the other end.
* **Tax Check** — a separate screen, cross-references a **rate list** (arrival/departure
  dates per room) against a **tax report**. Only run on nights where the main courante
  did not balance.

Alongside it: a nightly checklist with a desktop overlay, room nicknames, a watchlist,
per-user profiles, and `rc-tbind.exe` — a native helper that binds mouse buttons and key
combinations to protel shortcuts.

### The τ shortcut, the thing that has cost the most time

protel's invoice list jumps to the `ΤΕΛΟΣ ΑΝΘΕΚΤΙΚΟΤΗΤΑΣ` entry when you press the Greek
letter τ. It ignores an injected Unicode τ — it wants a real keystroke. So the helper
presses the **physical T key while Windows believes the keyboard is Greek**, then puts
the layout back. Everything hard about it follows from that.

## 3. How a release works

The workflow fires on a push touching `dist-win64/parts/**` or the workflow file. It
reassembles the parts, checks the sha, and republishes the tag.

`gh release create --latest` without `--target` tags the **default branch**, so a release
cut from a feature branch points at the wrong commit until it is merged. Merging fixes
it. This is why the workflow runs twice per release and that is fine.

### Building the installer (in the container)

```
scratchpad/stage/            the unpacked Electron payload, byte-for-byte from 1.11.5
scratchpad/reccheck.nsi      reconstructed NSIS script (NSIS 3.09-4, not electron-builder)
```

1. bump `app/package.json`, `APP_VERSION` in `app/index.html`, `DisplayVersion` in the .nsi
2. `cp app/index.html "Departments Check.html"`
3. copy the nine files into `scratchpad/pack/`, `npx asar pack pack stage/resources/app.asar`
   (files.js, index.html, main.js, overlay.html, overlay-preload.js, package.json,
   preload.js, tray.ico, updater.js — 1.17.10 briefly made it eleven; 1.17.11 moved the
   Caps Lock icon into the helper and took it back to nine)
4. `cp app/rc-tbind.exe stage/resources/`
5. `makensis reccheck.nsi` — takes ~7 minutes, run it in the background
6. **unpack the result and verify it** before splitting
7. `split -b 20971520 -d -a 3` into `dist-win64/parts/`
8. update `VERSION` + `SETUP_SHA256` in the workflow and `update/latest.json`

### Two kinds of update

* `type: "full"` — 90 MB installer. Needed whenever `main.js`, `preload.js`, the helper or
  anything outside the page changes.
* `type: "html"` — ~370 KB. Only `Departments Check.html`. `engine` names the minimum
  engine version; an older engine takes the full path instead and can never strand itself.

An html update is promoted only if its version beats the installed `pkgVersion`, so
`APP_VERSION` in the page and `version` in the manifest have to move together.

## 4. Landmines — every one of these cost real time

* **ASAR integrity.** The shipped exe carries an `/INTEGRITY/ELECTRONASAR/` resource, but
  the fuse `embedded_asar_integrity_validation` is **DISABLED** (sentinel
  `dL7pKGdnNz796PbbjQWNKmHXBZaB9tsX`). Repacking `app.asar` is therefore safe. Verify
  before assuming.
* **Mono's BCL is bigger than .NET Framework's.** `mcs` compiles against Mono; the helper
  runs on .NET Framework 4.8. `body.Split(',')` bound to `String.Split(char,
  StringSplitOptions)`, which 4.8 does not have — the JIT resolves every token in a method
  before running it, so the whole of `ParseBind` threw `MissingMethodException` on first
  call and the helper died 53 ms in with exit `0xE0434352`. Hidden for three versions
  because a second bug meant nothing was ever bound, so the helper never started. **This
  is what `build-check.py` exists to prevent.**
* **`display:none` in a stylesheet is not cleared by `style.display = ""`.** That only
  removes the inline override. `#notThereBtn` was never once visible. Toggle a class.
  And **assert on `getComputedStyle`, never on `el.style.display`** — the latter reads
  `""` precisely when the rule is hiding the element.
* **raw.githubusercontent caches the manifest ~5 minutes per regional edge.**
  `cache: "no-store"` does not bypass it; a unique query string does. This hid two
  releases.
* **An `HKL` is `(device << 16) | language id`.** Comparing whole handles reports a
  working layout hop as failed. Compare the low word.
* **`GetKeyboardLayout(0)`** reports the *calling* thread's layout. A thread id of 0 made
  a hop that never happened look successful.
* **`SendInput` is not synchronous.** Checking the queue immediately after it returns
  reads empty because the key has not arrived yet, not because it was consumed.
* **The two page copies drift.** `Departments Check.html` was left at a pre-1.16.1 state
  and would have shipped a downgrade. The workflow now `cmp`s them.
* **The script blocks are IIFEs** — nothing is on `window`. To test, inject a probe before
  the final `})();` on a copy.
* **jsdom needs an http origin** for `localStorage`; on `file://` it throws.

## 5. The build guard

`app/build-helper.sh` compiles and then runs `app/build-check.py`, which reads the
compiled assembly's `#Strings` heap and fails on any name not in `app/bcl-allow.txt`.

Adding a name to that file **is** the moment to confirm the member exists in .NET
Framework 4.8, because nothing else in the build will tell you. It is a name-level check,
not a signature-level one — a tripwire, not a proof. It also flags our own new method
names, which is the accepted cost.

Reintroducing the `Split` bug makes it exit 1 naming `StringSplitOptions`.

## 8. Where things stand

### The helper stands on its own (rc-tbind v10, 1.17.11)

`rc-tbind.exe` was a child of RecCheck: spawned with the bindings on its command line,
killed by its own watchdog two seconds after RecCheck exited. It is now a login program.

**What he asked for, in his words:** *"make rc-tbind.exe to work on its own, however
protel's shortcuts will work only when both rc-tbind.exe and reccheck.exe are running
simultaneously"* and *"the caps lock indicator will work regardless of reccheck running
or not"*. Do not quietly re-couple these.

* **Caps Lock: always.** The keyboard hook is unconditional — it is what sees the key
  while protel has the focus, and this job does not care whether RecCheck is open.
* **Shortcuts: only alongside RecCheck.** `hostUp` comes from
  `Process.GetProcessesByName("RecCheck")`, polled every 2 s on the old watchdog thread.
  Nothing is read from RecCheck and nothing is sent to it; its presence is the signal.
* **The mouse hook's lifetime still matches RecCheck's.** `SetHost` installs it when
  RecCheck appears and unhooks it when RecCheck goes — deliberately, so a machine with
  the tool closed carries no mouse hook at all, exactly the scope it had before this
  change. That was the one thing worth protecting when making it a login program.
  Keyboard triggers get an explicit `hostUp` check instead, because that hook stays up.
* `SetHost` and `LoadBinds` run on the **loop thread** (posted from the watcher), because
  a low-level hook belongs to the thread that installs it and only that one pumps.

**The bindings moved from the command line to a file**, since nothing hands this process
arguments at login: `%LOCALAPPDATA%\RecCheck\rc-tbind-binds.txt`, one token per line, the
same words that used to be arguments. `ParseBind` is untouched. The watcher re-reads on a
write-time change, so changing a binding in the app takes effect without a restart.

**The login entry** is `HKCU\...\Run\RecCheckHelper` — no admin, nothing installed. Verbs:
`install`, `uninstall`, `stop` (stand down without touching the entry — RecCheck asks for
this while listening for a button to bind, so the standalone's hooks cannot swallow the
press), `status` → `RCTBIND <on|off> <running|stopped> <ver>`. The NSIS uninstaller runs
`uninstall` **before** deleting the exe, or Windows is left starting a file that is gone.

**The icon is drawn in raw GDI, by hand, and that is not an aesthetic choice.** Mono's
class library is larger than .NET Framework 4.8's; WinForms or System.Drawing would have
put a large BCL surface behind `build-check.py`'s name-level tripwire, which is a
tripwire and not a proof. P/Invoke into user32/gdi32 carries no such risk. Two passes:
white silhouette (pen and brush), then the glyph in dark with a null pen — GDI strokes
*over* its fill and would otherwise close the counter of the A, where the app's SVG used
`paint-order="stroke"`. Checked side by side against the old SVG in Chromium.

**A failed window is not fatal.** If `CreateCapsWindow` fails there is no icon and no
cross-process single-instance check, but the shortcuts still work — `PostUi` falls back
to `PostThreadMessage` and the loop handles those messages itself.

**What could NOT be verified from the container** — no Windows here, and say so rather
than implying otherwise:
* the layered/colour-keyed window actually rendering, and the fade
* `GetKeyState`'s one-time seed of `capsOn` (thread-local). If the FIRST flash after a
  start says the wrong word, invert the seed; every flash after it is the hook's.
* `hostUp` transitions against a real RecCheck starting and stopping

**What WAS verified:** `rc-tbind.exe` rebuilt from the pre-1.17.10 source came out
byte-identical to the shipped binary (sha256 `3ffa4519…`), so the reversion of the
1.17.10 caps experiment was exact; `build-check` passes; the binds file written by
RecCheck's real `writeBinds()` was handed to the shipped exe and parsed by reflection into
the same four bindings, needle, `tau:50`/`thenEnter`, and the malformed-`tau` rejection;
the glyph coordinates were lifted out of the C# and rendered against the app's own icon.

### The "leaving today" mark on a search result (1.17.12)

A receipt on a room that is due out today: the guest charged something and only then came
to the desk, so it has to be settled before they walk. The whole match bar goes red — his
choice over a corner marker — with a LEAVING TODAY pill and a red arrow beside the
checkbox, where the eye already is.

**The name is the safety condition, and it is not optional.** In his words: *"if i have
two receipts for the same room number but different names then the name that has a
departure date of today is the one i want marked, dont accidentally mark the arrival
receipts (i rip those and throw them, so please, careful)."* A room leaving today may
already be re-let to somebody arriving today; marking that arrival's receipt would make
him destroy paper he needs. So `isLeaving(room, name)` requires BOTH a ledger entry whose
departure equals tonight AND `sameName()` — the strict comparison, not the tolerant one.

`leavingIndex()` is built once per search rather than per card, because it reads
localStorage.

Covered by a test that drives the shipped functions lifted out of index.html:
`scratchpad/leaving.js`, 18 cases. The one that matters is first — same room, SMITH
leaving today and JONES arriving today, and only SMITH's receipt is marked. Near misses
(surname only, extra initial, SMITHE), blank names on either side, a departure yesterday
or tomorrow, an unknown room, an empty ledger and an unreadable report date all mark
nothing.

**It was shipped with a warning that turned out to be wrong, and the correction matters
more than the warning did.** It was built with "this rides on a ledger that produces
phantom departures, expect false reds". He corrected that: *"the departures were always
okay, the arrivals are phantom, not the departures"* and *"they were always okay after the
first fix"* — i.e. departures have been sound since 1.17.9 removed the truncation rule.

The mark keys on `departure == tonight`, so it rides on the HALF OF THE LEDGER THAT WORKS.
Treat it as trustworthy. Do not re-add a "this may be wrong" caveat to it on the strength
of the arrival bug; they are different fields and different failure modes.

The one latent risk left is a room orphaned by a move: its entry is never closed, so on
the guest's ORIGINAL departure date it can fire a departure for a room they left days
earlier. That date is in the future when the move happens, which is why it has never
shown up in his panel — and for it to produce a false RED it would also need a receipt in
the old room under that same guest's name, which is unlikely since they are charging to
the new room. Latent, not observed.

### The tau -> Enter delay: where the time actually goes

Asked on 01/09 ("is there a soft cap to how fast i want it to be?"). Answer, from the code:

* the Enter is sent `gap` ms after `SendGreekT()` RETURNS. That call has already hopped the
  layout to Greek, pressed T, WAITED for the keystroke to leave the input queue, and
  hopped back. So felt latency = SendGreekT + gap, and against a busy protel the first
  term dominates. Lowering 50 does very little.
* the caps do not agree across the layers, which is worth knowing before touching them:
  the number box is `min=0 max=2000`; `sc-tauenter-set` clamps 0-2000 and SILENTLY keeps
  the old value outside that; `tauEnterConfig` accepts 0-5000; the helper's `tau:<ms>`
  accepts 0-5000 and REJECTS THE WHOLE BINDING outside it (no tau at all). 0 is safe.
* **the measurement already exists on his machine.** Every real press appends to
  `rc-tbind-tau.log`: "took N ms (waited N ms for the previous press)" plus the
  step-by-step. PROTEL SHORTCUTS -> the log button prints it, with Copy. Read that before
  changing any number. The Test button is NOT the same thing: it runs against an idle
  protel, the one state this has never failed in.

### A room move is INDISTINGUISHABLE from an arrival in the report — measured, 01/09

His real Rate Check for 01/09 was parsed here with the shipped `parseRate`. He identified
rooms 148, 263 and 535 as guests he had MOVED that day. Their rows:

```
[ARRIVAL] 112   112 | name | 01/09/26 | 12/09/26 | 2000 | 196,20 | HB | SCHAUINSLAND
[MOVED  ] 148   148 | name | 01/09/26 | 04/09/26 | 3000 | 344,40 | BB | TUI
[MOVED  ] 263   263 | name | 01/09/26 | 07/09/26 | 2000 | 188,00 | BB | ITS Coop
[STAYING] 177   177 | name | 29/08/26 | 05/09/26 | 1000 | 160,72 | HB | TUI SUISSE
```

Same eight columns, same x positions, arrival dated today. Occupancy, rate, board and
agent say nothing. **protel closes the old room's stay and opens a NEW one on the new room
dated from the move.** So "arrival dates follow the guest, not the room" holds while a
guest stays put and NOT through a move — he had it the other way round, and this is the
fact that explains the whole thing. 29 arrivals shown = 26 real + 3 moves.

### The row-merge diagnosis was WRONG — refuted by measurement, 01/09

Six agents and an adversarial pass concluded that `toRows` merges two printed lines and
`parseRate` then takes the room from one and the dates from another. His real file kills
it. Do not resurrect it:

* **every data row carries exactly 2 dates.** Never 3, in 233 rows.
* **the date columns are fixed**: arrival at x=240, departure at x=312, all 233 rows.
* **no row contains two room cells.** Nothing merged.
* **line spacing is ~19 units** against `toRows`' `<6` threshold — nowhere near merging.
* 227 rooms, 227 rows, **zero reversed or missing date pairs**.

Binding the dates to their columns — the fix that was going to be written — would change
NOTHING, because column order and print order already agree.

Also found: six rows are silently dropped, all 4-digit house accounts
(`9005 9040 9601 9604 9605 9608`, most running 18/04→10/11). The `/^\d{2,3}$/` room filter
excludes them. Correct, but they are invisible to the tool.

Also: **no room in a Rate Check departs on the day of that list.** It is a pre-EOD
in-house list, so tonight's departures were learned from YESTERDAY's list. By design, but
load-bearing for the 1.17.12 "leaving today" mark, which can only fire on rooms an earlier
night taught the ledger.

### Which half of the ledger is wrong — settled by him, 01/09

**Departures: correct, and have been since 1.17.9.** *"they were always okay after the
first fix."* Do not go hunting there.

**Arrivals: the phantom ones.** A guest who arrived 28/08 and moved rooms on 01/09 showed
as an ARRIVAL tonight, while the rate list plainly prints 28.08 against the new room —
because arrival dates in protel follow the GUEST, not the room.

That split is itself the strongest evidence for the row-merge diagnosis below, and it was
not what the diagnosis was fitted to: a merged row gives the room its NEIGHBOUR's arrival
(tonight, so a phantom ARRIVED) while its own real arrival is demoted into the DEPARTURE
slot, where it is a past date and fires nothing. Phantom arrivals with clean departures is
the mechanism's own signature. The mirror orientation would produce a false departure
instead, and he does not see those — which says the orientation is fixed, not random.

`rc-tbind.exe scan <pid> [delayMs]` — walks the foreground window and prints class, control
id, size, visibility, caption, and for list controls the **row count including rows
scrolled out of sight**. Behind DEBUG with a five-second countdown, output copyable. Wired
through `sc-scan` IPC and `reccheckShortcuts.scan()`.

It exists as commit **`7171f47`**, which is **not on any branch** — recover with
`git cherry-pick 7171f47` or `git checkout 7171f47 -- app/`. It was never built into an
installer and never shipped, because he raised the vendor-managed constraint immediately
after and the risk question was put to him unanswered.

**What it touches.** `EnumChildWindows`, `GetClassName`, `GetDlgCtrlID`, `GetWindowRect`,
`IsWindowVisible` are window-manager reads that never reach protel's code. `WM_GETTEXT` and
the row-count messages **do** enter the target's queue — answered by USER32 and comctl32 for
standard controls. Where protel paints its own lists there are no child windows and nothing
is sent at all.

The question it answers, which no screenshot can: **are protel's grids real Windows
controls?** Verified from his filter-dialog screenshot that protel's *dialogs* are standard
Win32 controls, so it is a native app; the grids are still unknown.

### The live feed — design settled, nothing built

He wants RecCheck reading protel continuously, feeding a shift-aware overlay: arrivals with
times (morning shift shows those landing early enough to reach the desk by 15:30, afternoon
by 22:30 — the `T.` column is the flight time, +2h for transfer), departures beside them
vanishing once their time passes, no-times hidden, and room moves picked up as they happen.

Conclusions reached, so they are not re-litigated:

* **Printing the lists is ruled out.** Already recorded below — a printed list goes stale
  inside the day and the desk corrects it in pen.
* **No live read of protel is zero-touch.** Reading window contents means messages or UI
  Automation. The choice is which mechanism and how much is verified first.
* **Diff the state, do not watch for clicks.** Click-watching only catches actions taken on
  that PC by that user; a colleague or head office voiding a reservation elsewhere produces
  nothing. A state diff catches every change regardless of who made it or how.
* **`SetWinEventHook` out-of-context** is the mechanism for "every window that opens" — the
  callback runs in OUR process, Windows marshals the events, nothing is injected into
  protel. Read once, ~400 ms after `EVENT_OBJECT_SHOW` so the window has finished building.
  Never re-read: read-once-at-open is bounded by human action (~200 windows a shift), where
  polling is not.
* **Watching for a window is zero-touch**; reading its fields is not. `GetWindowText` on
  another process's top-level window returns the cached caption without sending a message.
  So "the date-change dialog opened" is detectable with nothing sent to protel at all.
* **A no-show and a cancellation both vanish from today's arrivals.** They differ in that
  the no-show reappears tomorrow. There is a live void list in protel that would make a
  cancellation a fact rather than a deduction — prefer reading it over inferring.

**Two decisions put to him and not answered:** the log would contain guest personal data,
and it would record what his colleagues do at a shared desk. Both are choices far cheaper
to make before building than to unpick after.

### Solved — what the τ intermittency actually was (1.17.3)

**It was never the shortcut.** He worked it out at the desk: he presses Enter immediately
after the τ, and protel has not finished reacting to the τ yet, so the Enter is lost. The
symptom — "the first press does nothing, the second works" — was one keypress arriving too
early, not a keypress that never arrived.

The clincher is his own observation: *the invoice shortcut always works no matter how fast
I press it.* That one is `seq:` — a run of keys the helper times itself, with a fixed gap.
protel is never rushed there because a person is not in the loop.

So the τ now does the same: the `tau` action takes an optional follow-up, spec `tau:<ms>`,
and after the layout is back it waits and presses Enter. Default 100 ms, on, with a
checkbox in PROTEL SHORTCUTS to turn it off. The delay is data in config
(`c.tauEnter = {on, delay}`) travelling on the command line, so retuning it does not mean
another helper.

A malformed `tau:<ms>` is **rejected outright** rather than degrading to a plain τ — a bind
that silently does half of what it says is worse than one that does nothing.
`scratchpad/tauenter.cs` drives `ParseBind` through reflection over ten specs.

Worth remembering how much this cost: three releases guessing at layout hops, drain
bounds and focus, two diagnostic runs that came back perfectly clean, and a press recorder
built to catch a failure that was never going to appear in the log — because nothing was
failing. **The clean diagnostic was the answer, not a dead end.** When instrumentation
insists everything worked, believe it, and go looking for what happens *after* the part
you instrumented.

### The protel-only gate (1.17.2)

A bound side button is still a mouse button in every other window on the machine, so
`bind` now takes an optional `focus=<needle>`: a trigger fires only while the foreground
window matches that needle on its **process name, class or title** — any one is enough,
matched uppercase. Blocked presses are **passed through, never swallowed**, so the button
keeps doing whatever it normally does; a window we can read nothing about is allowed
through, because a gate that cannot see must never be why a shortcut stopped working.

The needle is never guessed. PROTEL SHORTCUTS has a checkbox and a *Point it at protel*
button: five seconds, the user brings protel forward, `rc-tbind fg` prints
`FG<tab>exe<tab>class<tab>title`, and the process name becomes the needle. Ticking the box
with nothing stored runs that pick first. Off until they do it — a needle matching nothing
would swallow every shortcut mid-shift.

Every blocked trigger writes one line per foreground window into the press log, so
**DEBUG → What the last presses did** says "trigger ignored: protel was not in front"
with what *was* in front. That is how a wrong needle announces itself.

The picker refuses to aim at RecCheck itself. Not alt-tabbing in time is the likeliest
way to get this wrong, and it would stop every shortcut working in protel; `sc-focus-pick`
compares the picked process against `process.execPath`'s last segment and returns
`self: true`, and the page says so instead of storing it.

`MatchesNeedle(exe, cls, txt)` is deliberately free of Win32 so it can be tested off
Windows — `scratchpad/focus.cs` drives it through reflection, thirteen cases.
`scratchpad/mainfocus.js` drives the real `main.js` with electron and `child_process`
stubbed and asserts on the command line the helper is actually spawned with.

Known simplification: the decision is cached per `HWND` for the life of the helper. A
handle Windows recycles onto a different window would keep the old answer until the
foreground changes again. One shortcut firing where it should not, in a case that needs a
window to close and its exact handle to be reissued — which is what happens today anyway
with no gate at all. A tick-count bound on the cache would close it if it ever matters.

### The room movements panel — what 1.17.1 was about

The symptom was: rate list loaded, department check opened, no pills. The cause was that
`saveMoves` returned immediately without a business date, and that date came from exactly
one row — page one, matching `/PROTEL HMS/`, with a `dd/mm/yyyy` cell beside it. A list
whose header differs parses its rooms, loads without complaint, and writes not one
reservation.

`parseRate` now tries four things in order: that row, any header row naming protel, the
date printed most often in the file, and the newest arrival in the list itself. Only the
last is a guess and `dateSure` marks it — a guessed date may stamp a reservation but may
never truncate a stay. The rate slot says what went into the ledger at the moment of
loading, and **DEBUG → Why the room pills say what they say** prints the report night,
what the last list recorded, the ledger's span, and every stay within three days of
tonight.

If pills are still missing, that report answers it: either the ledger is empty (the write
half) or the dates do not line up (the read half). Do not guess between them.

### The home screen fits the window (1.17.4)

The rule that makes it work, and the one that broke it twice while getting there:

* **The chain has to be definite the whole way down.** `min-height` gives a flex child
  nothing to shrink *against*, so the column just grows and the overflow moves somewhere
  else. The body itself is the column on this screen (`body.onMenu`), header then page,
  and every link down to `#clList` is flex with `min-height:0`. Only two of the body's
  children are ever in flow here; everything else is `display:none` or fixed.
* **Auto side margins stop a flex item stretching.** `#homeBar` and `#checklist` are both
  `margin:0 auto`, so as flex items they shrank to their contents — 640px down to 383 and
  303 — and stopped lining up with the button below. `width:100%` restores it. Without it
  the bar is only as wide as its buttons and would never wrap however many categories it
  grew, which was half the point.

`#clList` is the only part allowed to scroll, and it says so: `paintListFade()` toggles a
`moreBelow` class (a mask-image fade on the bottom row) on render, on scroll and on
resize. A list that hides tasks with no cue is worse than a long page.

Verified in real Chromium via playwright-core against `/opt/pw-browsers` — jsdom does no
layout, so it cannot answer this question at all. `scratchpad/fit.js` walks six window
sizes × four list lengths asserting the page fits and the audit button is on screen;
`fit2.js` covers the dropdowns (the page can no longer scroll to reveal one that hangs
past the bottom), edit mode, the other screens being untouched, and live resizing;
`fade.js` covers the cue; `cmpshot.js` diffs the box geometry against the previous
release, which is what caught the auto-margin regression.

### Fitting the window is not the same as showing everything (1.17.5)

1.17.4 made the home screen fit the window and I called that done. It was not what was
asked for: a 640px strip down the middle of a 1600px screen still hid twenty tasks behind
a scroll. *"Fit everything in a glance"* meant **use the width**.

`layoutChecklist()` measures the space a column actually has — the gap between the top of
`#clList` and the top of `#auditBtn`, both stable whatever the column count, so it does
not chase its own tail — and flows the list into as many columns as fit, down one column
then across. `--homeW` widens the bar, the card and the audit button together; `--clRows`
sets the column height. One column is exactly the old 640px layout.

Two things worth keeping:

* **The card must never get NARROWER than 640px.** Two columns at 268px each computed to
  594 and the block visibly shrank as tasks were added. Floor it.
* **Don't trust the arithmetic — look.** Rows are not all one height once a title wraps,
  and the row-count sum was off by one often enough to leave a task hidden. After applying
  a column count it now checks `scrollHeight > clientHeight` and takes another column if
  there is width for one. Bounded by the width cap, so it terminates.

The gutter that "Switch user" parks in is reserved against the **window**, not against
`#landing` — the card is centred on screen, so the space either side of it is what counts.
Reserving against `#landing` cost a whole column at 1366px.

### Dialogs used to grow past the window (1.17.5)

`#modal` had no `max-height` and no scroll, and `#modalBg` centres it — so a dialog taller
than the window was cut off at **both** ends with no way to reach either. PROTEL SHORTCUTS
was already 970px tall at 1.17.2, past every window height tested; the focus gate and the
τ box took it to 1192 and the Done button became impossible to reach. Now the modal is
capped to the window and scrolls inside itself, and `.actions` is sticky at the bottom so
the way out of a dialog is never something you have to go looking for.

`#modal:has(.actions){padding-bottom:0}` hands the modal's bottom padding to the sticky
row — without it the row floats 22px up with content still showing underneath.

### Adding a bindable action

Four places, and missing any one of them fails quietly rather than loudly:

1. `app/tbind.cs` — an `ACT_*` constant, a branch in `ParseBind` for the spec token, and a
   branch in `QueueSend`. Alt-combinations go through `SendAltKey(vk)`, which releases
   whatever the user is physically holding first: the trigger may itself be a
   modifier+button combination, and protel would otherwise see Ctrl+Alt+N.
2. `app/bcl-allow.txt` — the new names, then rebuild through `build-helper.sh`.
3. `app/main.js` — `ACTIONS`. This drives the spec built for the command line, and
   `sc-detect` validates against it, so a name missing here cannot be bound at all.
4. `app/index.html` — `SC_ACTIONS` for the row order, plus `sc.<name>` and
   `sc.<name>Why` in **both** language tables.

It is a full installer: the helper and main.js both change.

### A nickname belongs to the guest, not the room (1.17.7)

He settled the ambiguity: the nickname is about the **guest**. And the department report
only ever lists rooms that were *charged*, so the room somebody moved out of is simply
absent — there is no event to read. The nickname used to sit on that empty room for ever
while the guest's new room got none.

`syncRooms()` now looks for the move: if the name charging a room is **exactly** the name
that carried a nickname in another room tonight or last night, and that other room is not
still charging under it, the nickname goes with them. His call on exact matching, and the
right one — `sameGuest()` answers "could this be the same person", which is correct when
shortening a stay and wrong here. Carrying a label onto the wrong guest is worse than not
carrying it. `sameName()` trims, collapses whitespace and case-folds, none of which can
make two different names match.

Two guards, both strict, both tested:

* the old room **still charging** under that name is not a move — that is one party across
  two rooms;
* **two rooms holding the same name** is not evidence of anything, so an ambiguous match
  moves nothing at all.

`tonight` and a `before` snapshot are both built in full before anything is written: a
room change is a question about two rooms at once and cannot be answered halfway through
updating the first. `prevNightKey()` decrements through a real Date, so month and year
ends work.

It announces itself — moving someone's label between rooms is exactly the sort of thing
that must be visible the night it happens.

**Out of scope, by his decision:** a guest who moves and then charges nothing in the new
room that night is invisible to this report, so the nickname stays put until they do
charge. That is not what he uses nicknames for. Do not go building a rate-list path to
close it.
