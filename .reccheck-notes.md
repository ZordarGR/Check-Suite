## 1. What the tool is

An Electron 43.2.0 app that audits a night's POS receipts against protel's
`checkcharge1` report (`ΕΛΕΓΧΟΣ ΤΜΗΜΑΤΩΝ BY ROOM`, saved as `.oxps`). Two tools in one
page:

* **Department Check** — the receipt audit. Loads the `.oxps`, lists receipts per
  department, you search each paper serial and tick it. Corrections, manual entries and
  a printed sheet for reception come out the other end.
* **Tax Check** — a separate screen, cross-references a **rate list** (arrival/departure
  dates per room) against a **tax report**. Only run on nights where the main courante
  did not balance.

Alongside it: a nightly checklist with a desktop overlay, room nicknames, a watchlist,
per-user profiles, and `rc-tbind.exe` — a native helper that binds mouse buttons and key
combinations to protel shortcuts.

### The τ shortcut, the thing that has cost the most time

protel's invoice list jumps to the `ΤΕΛΟΣ ΑΝΘΕΚΤΙΚΟΤΗΤΑΣ` entry when you press the Greek
letter τ. It ignores an injected Unicode τ — it wants a real keystroke. So the helper
presses the **physical T key while Windows believes the keyboard is Greek**, then puts
the layout back. Everything hard about it follows from that.

## 3. How a release works

The workflow fires on a push touching `dist-win64/parts/**` or the workflow file. It
reassembles the parts, checks the sha, and republishes the tag.

`gh release create --latest` without `--target` tags the **default branch**, so a release
cut from a feature branch points at the wrong commit until it is merged. Merging fixes
it. This is why the workflow runs twice per release and that is fine.

### Building the installer (in the container)

```
scratchpad/stage/            the unpacked Electron payload, byte-for-byte from 1.11.5
scratchpad/reccheck.nsi      reconstructed NSIS script (NSIS 3.09-4, not electron-builder)
```

1. bump `app/package.json`, `APP_VERSION` in `app/index.html`, `DisplayVersion` in the .nsi
2. `cp app/index.html "Departments Check.html"`
3. copy the nine files into `scratchpad/pack/`, `npx asar pack pack stage/resources/app.asar`
   (files.js, index.html, main.js, overlay.html, overlay-preload.js, package.json,
   preload.js, tray.ico, updater.js — 1.17.10 briefly made it eleven; 1.17.11 moved the
   Caps Lock icon into the helper and took it back to nine)
4. `cp app/rc-tbind.exe stage/resources/`
5. `makensis reccheck.nsi` — ~5 minutes, run it in the background. **Wait on the process,
   not on the call.** Backgrounding it a second time (`nohup … &` inside an already
   backgrounded call) reports exit 0 the instant the shell forks, and the half-written
   `RecCheck-Setup.exe` sitting there looks like a finished 7 MB build. Poll `pgrep -x
   makensis`. A real one is ~93 MB; the log's last line is `Total size:`.
6. **unpack the result and verify it** before splitting — `7z x` the installer, then
   `npx asar extract` the `resources/app.asar` inside it and check `APP_VERSION`, the file
   count, and that the page is byte-identical to `app/index.html`. `strings` proves
   nothing: the payload is solid LZMA, so nothing inside it is greppable, and neither is
   the `DisplayVersion` the .nsi writes.
7. `split -b 20971520 -d -a 3` into `dist-win64/parts/`
8. update `VERSION` + `SETUP_SHA256` in the workflow and `update/latest.json`

### Two kinds of update

* `type: "full"` — 90 MB installer. Needed whenever `main.js`, `preload.js`, the helper or
  anything outside the page changes.
* `type: "html"` — ~370 KB. Only `Departments Check.html`. `engine` names the minimum
  engine version; an older engine takes the full path instead and can never strand itself.

An html update is promoted only if its version beats the installed `pkgVersion`, so
`APP_VERSION` in the page and `version` in the manifest have to move together.

## 4. Landmines — every one of these cost real time

* **Clicking a button in RecCheck makes RecCheck the foreground window.** Obvious once
  said, and it made the whole live-feed button dead on arrival in 1.17.27: `ReadInhouse`
  opened with `GetForegroundWindow()`, so the press it was reacting to had already put
  RecCheck in front and the read came back "that is not protel". DEBUG's `readlist` gets
  away with the foreground only because it counts down first and he switches over — a
  button has no such moment. **He ran it, got exactly `protel said: that is not protel`,
  and then asked the question that located it** — "does it take the list from whatever
  window is in front?" The failure was on his screen; the code answered why. (An earlier
  note here said he found it by asking rather than by running. He ran it. Corrected.)
  Anything triggered from RecCheck's own UI must find its target window by hunting for
  it, never by asking what is in front.
* **A stub can hide the only thing that matters.** `test/browser/live.js` proved the
  parsing, the refusals and the ledger writes — and stubbed the bridge, which is exactly
  where the bug was. Everything downstream of `window.reccheckShortcuts.inhouse()` was
  correct; the call could never return anything. **This class of fault — whether the
  helper is looking at the right window at the moment it is asked — is not testable in
  this container at all**, and no harness here should be described as covering it.
* **In an MDI app, the biggest list under the frame is not the list in front.** protel's
  reports are MDI children. A restored window sits on top of a maximised one, so picking
  the largest `SysListView32` under the frame reads the window BEHIND. And the frame's
  caption names a child only while that child is maximised — restore it and the caption
  names nothing, so the read cannot even report which list it got. Scope to the active MDI
  child (`MDICLIENT` → `GetWindow(…, GW_CHILD)`) and report THAT window's caption. Found
  by him on the second live run, before a line of it was wired to the ledger.
* **A tripwire that matches one syntax checks only that syntax.** `test/scopecheck.js`
  compared the two language tables with a regex for QUOTED, DOTTED keys (`"menu.audit":`)
  — the shape `T` uses. `I18N`'s keys are bare identifiers (`live_read:`), so all 112 of
  them, both languages, were invisible to the guard that exists precisely because keys had
  drifted into one language before. It now walks the literal instead of matching lines,
  skipping strings whole so a value like `"protel said: "` cannot be mistaken for a key.
  Found while adding two keys by hand to two tables — which is exactly the moment it was
  supposed to be watching.
* **ASAR integrity.** The shipped exe carries an `/INTEGRITY/ELECTRONASAR/` resource, but
  the fuse `embedded_asar_integrity_validation` is **DISABLED** (sentinel
  `dL7pKGdnNz796PbbjQWNKmHXBZaB9tsX`). Repacking `app.asar` is therefore safe. Verify
  before assuming.
* **Mono's BCL is bigger than .NET Framework's.** `mcs` compiles against Mono; the helper
  runs on .NET Framework 4.8. `body.Split(',')` bound to `String.Split(char,
  StringSplitOptions)`, which 4.8 does not have — the JIT resolves every token in a method
  before running it, so the whole of `ParseBind` threw `MissingMethodException` on first
  call and the helper died 53 ms in with exit `0xE0434352`. Hidden for three versions
  because a second bug meant nothing was ever bound, so the helper never started. **This
  is what `build-check.py` exists to prevent.**
* **A test that lifts a function by text proves that function, not its caller.** The
  movements panel showed nothing for two versions. A harness lifted `roomMoves` out of
  the page, drove it with a real ledger, produced correct pills, and I reported the panel
  was not broken. It was: `renderMoves` called `liveReceipts()`, which does not exist
  anywhere — the real name is `checkableList()` — so it threw a `ReferenceError` after
  appending its title and before the first pill, and `stage()` swallowed it. His own
  DEBUG report said `43 pills` while the panel was blank; that contradiction was the
  evidence and I did not read it. **Lift the function that is actually called, or check
  the scope.** The scope check below finds this in a second.
* **The tax half is namespaced; the audit half is not.** Everything under `#taxScreen`
  is prefixed, but the audit's own chrome is written on bare element selectors — `header`,
  `header h1`, `.btn`, `.acc`. The tax page has a `<header>` and an `<h1>` of its own, so
  it had been rendering them as the audit's sticky, blurred, bordered, amber-monospace,
  `white-space:nowrap` app bar since the two halves were merged. `#taxScreen header h1`
  only overrode the properties it happened to re-declare; the rest leaked. Between 901 and
  ~1090 px — where the help panel takes 300 px and leaves under 600 — that pushed the whole
  page past the window. **A rule under `#taxScreen` must state every property the bare
  selector sets, not just the ones being changed.** `.acc` still inherits the audit
  accordion's panel background and border; verified harmless on screen, so left alone.
* **One row could wipe the whole ledger, and nothing would say so.** The pruning loop in
  `saveMoves` took its floor from **the newest departure in the ledger** minus a year.
  That hands the decision to whatever the furthest-future row says. protel prints an
  open-ended reservation as `31/12/99`, and `dkey` (5288) reads a two-digit year as 20xx
  with no upper bound — so `31/12/99` is **20991231**. One such row set the floor to
  20981231 and deleted every real 2026 stay; the poison row survived the cull because its
  own date is above the floor, so **every later rate list wiped the ledger again**. The
  panel would have gone empty for ever with nothing on screen to explain it.
  Reproduced against the shipped code before changing it, and shown fixed after. The floor
  is anchored to the LIST'S OWN business date now — a real date no single row can drag —
  and with no date nothing is pruned at all. A stay with **no** departure date is also no
  longer dropped: `d||0` put every one of them below any positive floor, and a stay protel
  printed without a departure is not an old stay. **It was not firing on his ledger**
  (span 20260814..20260925, floor 20250925) — a landmine, not a live fault.
* **The 03:30 boundary is visible between 03:30 and 07:00, and only there.** At 06:46 on
  03/09 the tool's current night is 03/09, so a loaded 02/09 report is labelled amber
  "last night" where the old 07:00 boundary made it green "tonight". The file browser's
  TONIGHT badge (`bnKeyOf(f.mtimeMs) === bnKey()`) moves with it. Neither touches which
  pills are drawn — the set comes from `MODEL.reportDate` — but it is what he will see
  first if he reads the header as disagreement.
* **Do not derive a wall-clock boundary by subtracting absolute time.** Both day keys were
  `new Date(now - h hours)` read in local fields. Correct on 363 nights and a whole hour
  wrong on the other two: measured against Greece's real transitions, the shift reset went
  at **06:00** on 25/10/2026 and **08:00** on 28/03/2027, and the working night at 04:30
  instead of 04:00 in spring. Compare the local hour to the boundary and step the local
  DATE back instead — that cannot drift, because 07:00 is 07:00 on the wall whatever the
  offset did. On the spring night 03:30 does not exist, so the working night turns at
  04:00, the first local minute that does; that is right, not a compromise. `test/dst.js`
  fails on the old arithmetic and passes on the new.
* **He was right about the shape and it is worth keeping.** The reset is a stored day key
  compared on a 30 s poll, NOT a "fire at 07:00" condition — so a machine asleep or an app
  closed at 07:00 still clears at the next look, and a clock corrected by its time server
  is simply re-read. That half was never the fragile one. The bug lived entirely in how
  the key was derived.
* **The helper's pipe was never carrying anything but ASCII, so nobody noticed it was
  wrong.** `Say()` wrote through `Console.Out`, which encodes with the CONSOLE's code page
  — not UTF-8 on a Greek Windows — while `main.js` decoded the pipe as UTF-8. Every verb
  until now answered in ASCII (`RCTBIND OK v15`, hex handles, class names), so it never
  showed. The list read is the first thing to send a guest name back, and he said it
  himself: the list has Greek in it. It writes UTF-8 bytes straight to the handle now.
  **And the Node side decoded each chunk separately** (`out += d`), which destroys any
  character whose bytes land either side of a chunk boundary — all seven handlers collect
  the buffers and decode once. `test/stdout.js` splits a Greek name mid-character on
  purpose and checks it survives.
* **A blind search-and-replace across seven handlers broke four of them, and `node --check`
  passed.** They pushed into `chunks` while their closures still read `out`, a binding that
  no longer existed — a `ReferenceError` at the moment the user pressed the button, in code
  that parses cleanly. Same shape as `liveReceipts`. The harness drives the real handlers
  with electron and `child_process` stubbed, which is what caught it.
* **A P/Invoke whose return value is thrown away decides things by accident.** `readlist`
  opened protel with VM_OPERATION|VM_READ|VM_WRITE and no query right, then called
  `IsWow64Process(proc, out wow)` and **discarded the BOOL**. That call REQUIRES
  PROCESS_QUERY_INFORMATION or PROCESS_QUERY_LIMITED_INFORMATION, so it fails, never
  writes the out parameter, and `wow` stays false. `target64 = (IntPtr.Size == 8) && !wow`
  then answers TRUE on 64-bit Windows — while protel is `PROT32`. A 64-bit LVITEM handed
  to a 32-bit list control puts `pszText` in the alignment padding: **NULL**. On an
  owner-drawn list that null reaches protel's own `LVN_GETDISPINFO` handler. Found by the
  pre-push audit, confirmed by two more agents that tried to refute it, and never shipped.
  Now: the query right is asked for, both `IsWow64Process` calls are checked, the OS's
  bitness is established separately from ours, and **the read is refused rather than
  guessed** if either call fails.
* **A test of the parts is not a test of the choice.** `test/lvitem.cs` proved both LVITEM
  layouts were built correctly — seventeen assertions, all passing — and was blind to the
  wrong one being selected. `TargetIs64` is now a pure function precisely so the DECISION
  can be pinned, across all four combinations of OS and target bitness.
* **A guard with hardcoded line numbers stops guarding silently.** `test/scopecheck.js`
  sliced the page at `lines.slice(1322, 4937)` to find the renderer's IIFE. The page grew,
  the window drifted off the declarations, and it began calling declared things undefined.
  It searches for the block now. It also strips comments first — prose contains things
  that look like calls, and it was reporting `all` as undefined because a comment said
  "at all (65, 94, ...". A checker that cries wolf over its own commentary gets ignored.
* **A truncated diagnostic produces a truncated diagnosis.** `movesReport` printed
  "stays near this night" and cut it at 40 rows. On 02/09 that cut at room 153, and the
  conclusion drawn from it — that every pill above 153 must come from the name-change
  deduction — was right about the rooms it could see and wrong to be stated as the whole
  cause. Removing the deduction did not stop the phantom departures, because the OTHER
  source was never visible in the report: **stays whose recorded departure date is simply
  out of date.** Nothing is deduced now; a ledger entry written by an old rate list just
  keeps saying what that list said. 1.17.21 prints every pill with the date of the list
  that wrote it and counts how many are older than the newest, which is the difference
  between the two causes on one line. **Never diagnose from a report that elides.**
* **A name change is not a date. Third time.** 30/08: a rule that ended a stay when a
  room charged under an unrecognised name made 83 phantom departures. It was removed from
  the ledger writer — and the same inference survived in `roomMoves`, adding a dashed
  TURNOVER pill for any room whose department-report name differed from the cached one.
  On 02/09 the last rate list loaded was 31/08, so every real changeover of 01/09 and
  02/09 read as a name change: rooms **65, 94, 124, 129** — with no arrival or departure
  on that night in the ledger at all — were all claimed to have left and been re-let.
  Proved from his own DEBUG dump: those rooms are pills, and they are absent from the
  same dump's list of stays within three days of the night. **Dashed does not help — a
  turnover pill claims a departure.** Gone in 1.17.17. `ROOMS[].movedOn` is still stamped
  and now read by nothing.
* **A room number is not a stay.** The receipts dot on a departure pill was built from
  `effRoom(r)` alone, so any live receipt for that room number lit it. The moment a room
  turns over — and with no rate list since the arrival, a turned-over room still shows as
  a plain departure — the dot lands on the NEW occupant's receipts, which is paper he
  must not throw away. It matches on the departing guest's name now, through
  `leavingIndex()`/`isLeaving()`, the same index behind the red mark in the search
  results, which was specified against exactly this mistake.
* **`display:none` in a stylesheet is not cleared by `style.display = ""`.** That only
  removes the inline override. `#notThereBtn` was never once visible. Toggle a class.
  And **assert on `getComputedStyle`, never on `el.style.display`** — the latter reads
  `""` precisely when the rule is hiding the element.
* **raw.githubusercontent caches the manifest ~5 minutes per regional edge.**
  `cache: "no-store"` does not bypass it; a unique query string does. This hid two
  releases.
* **An `HKL` is `(device << 16) | language id`.** Comparing whole handles reports a
  working layout hop as failed. Compare the low word.
* **`GetKeyboardLayout(0)`** reports the *calling* thread's layout. A thread id of 0 made
  a hop that never happened look successful.
* **`SendInput` is not synchronous.** Checking the queue immediately after it returns
  reads empty because the key has not arrived yet, not because it was consumed.
* **The two page copies drift.** `Departments Check.html` was left at a pre-1.16.1 state
  and would have shipped a downgrade. The workflow now `cmp`s them.
* **The script blocks are IIFEs** — nothing is on `window`. To test, inject a probe before
  the final `})();` on a copy.
* **jsdom needs an http origin** for `localStorage`; on `file://` it throws.

## 5. The build guard

`app/build-helper.sh` compiles and then runs `app/build-check.py`, which reads the
compiled assembly's `#Strings` heap and fails on any name not in `app/bcl-allow.txt`.

Adding a name to that file **is** the moment to confirm the member exists in .NET
Framework 4.8, because nothing else in the build will tell you. It is a name-level check,
not a signature-level one — a tripwire, not a proof. It also flags our own new method
names, which is the accepted cost.

Reintroducing the `Split` bug makes it exit 1 naming `StringSplitOptions`.

## 6. Testing, since none of this can run on Windows here

* **`test/` holds them now** — `sh test/run.sh` runs every harness that needs nothing but
  node, and `test/browser/` holds the Chromium ones. Each drives the SHIPPED code, lifted
  by text or by reflection, never retyped. `node test/harness.js` regenerates the browser
  copy of the page; a stale one tests the wrong thing.
* **The real `main.js` with electron stubbed** — `Module._load` intercepts `require("electron")`,
  the stub captures `ipcMain.handle` and `globalShortcut.register` so the actual handlers
  and hotkey callbacks can be driven.
* **The helper under Mono** — `ping`, argument parsing and the crash reporter all work on
  Linux. Anything touching `user32` does not, and fails at `GetCurrentThreadId`.
* **Scope-check before believing a render test.** Thirty lines, rebuilt in the scratchpad
  when needed: slice out the IIFE that holds the renderer, collect every
  `function`/`const`/`let`/`var` declared in it, then report any `name(` call site that
  resolves to nothing. A silent `ReferenceError` inside a `stage()` looks exactly like
  "there was nothing to draw". It is not committed — see the queue.
* **Sweep layout with a real browser, not by reading CSS.** `playwright-core` and the
  Chromium at `/opt/pw-browsers` drive a probe-injected copy of the page (`window.__t`
  exporting the dialog openers and `showScreen`). Open each dialog and each screen at
  420/640/760/909/1280/1600 and compare `scrollWidth` with `clientWidth` on `#modal` and
  on `documentElement`. That is what found both 1.17.16 bugs, and what proved the other
  nine dialogs were fine. Exclude `#drawer` — it is parked off-screen by design.
* **The live read has two harnesses, and the second is the one that matters.**
  `test/inhouse.js` drives his five real rows through the shipped `inhouseToRate` and then
  the shipped `saveMoves` — 31 assertions, including that no travel agency reaches the
  ledger. `test/browser/live.js` presses the real button in Chromium with a stubbed bridge
  and requires the WRONG list to write nothing at all.
* **The installer is always unpacked and checked before splitting.**

### The room database on disk — BUILT, 1.17.31

His call, 04/09: *"we need the rooms that have been fed by protel to persist somewhere in
the tool's directory (if you can add encryption to this you would be amazing!)"* — and,
asked what strength: *"for now obfuscate them, later on if we decide to add accounts and
passwords to log into the app... we can use a hash from the password characters to serve
as the encryption key"*.

**This REVERSES the 03/09 "tonight only" decision, for names, knowingly and on his
instruction.** Guest names now sit on the hotel's PC between shifts. Worth having written
down as a deliberate reversal rather than a drift.

**It is obfuscation, and it is never called anything else.** `rooms.dat` in
`app.getPath("userData")`: a `RCR1` stamp, then a repeating-key XOR with the offset folded
in. The key is in the program, so anyone holding the exe holds the key. It stops the file
being read by opening it and nothing more. Told to him in those words before he chose it.

* **localStorage stays the working store.** The renderer boots off it synchronously; the
  file is a mirror written beside it and read back only to fill in what localStorage has
  lost. The running store wins every conflict — a stale file quietly replacing tonight's
  work is the failure that would matter.
* **Written to a `.tmp` and renamed**, so a crash mid-write cannot leave half a database.
* **Every failure path returns null**, never throws. The renderer treats null as "carry on
  with what you had", and an exception there would take the room database out with it.
* **Boot does NOT await it.** A boot that waits on an IPC round-trip is a boot that can
  hang on one. Opening a report does await it, which is the point where it has to be
  right — before `syncRooms`, or the ingest would create the room fresh from the CUT name.

**On his plan for a real key, since he asked.** Deriving it from a login password is sound
